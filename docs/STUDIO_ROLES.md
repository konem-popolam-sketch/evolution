# Роли субъагентов студии

Как устроены роли 50 субъагентов, как их назначать и почему роль нельзя менять
«по ходу». Источник правды по контракту — `docs/STUDIO_CONTRACT.md`.

## Что такое роль

Роль — короткий текст (≤ 200 символов), закреплённый за слотом субъагента в
`~/.dsh/agents/roles.json`:

```json
{
  "variant": "1",
  "slots": {
    "technical-director": { "role": "архитектура, технологии", "assignedAt": "2026-10-30T04:00:00.000Z", "source": "base" },
    "qa-tester": { "role": "", "assignedAt": null, "source": "base" }
  }
}
```

- `base` — роль из `roster.json` (поле `fn`), выдана при первом запуске;
- `assigned` — роль, назначенная капитаном через API;
- пустая строка `""` — роль ещё не назначена (у 38 слотов после базовых 12).

Роль видна в карточке субъагента в комнатах студии и используется в его
`executionPrompt` («прочитай свою роль и память»). Память слота —
`~/.dsh/agents/memory/<slot>.md`, см. `studio/memory-template.md`.

## Правило: роль закрепляется навсегда

**Назначенная роль постоянна.** Субъагент — это личность с историей: он копит
память «что делал», и смена роли обнуляет смысл этой памяти.

- Менять роль можно **только по прямой просьбе пользователя** (или капитана,
  действующего по его поручению). Сам субъагент свою роль не переписывает.
- Если роль пуста и субъагент считает, что она ему нужна — он **предлагает**
  формулировку капитану в отчёте, а не назначает себе сам.
- Если роль не подходит к задаче — задача отдаётся другому слоту, а не
  переписывается роль существующего.
- Переопределение роли фиксируется в `roles.json` (`source: "assigned"`,
  `assignedAt` — ISO-время). Старую формулировку в память не переносим.

## Как назначить роль: `POST /role`

Хост-половина плагина (`studio/roster/index.js`) поднимает маршрут на веб-сервере
DSH:

```
POST /plugins/dsgs-agent-roster/role
Content-Type: application/json

{ "slot": "qa-tester", "role": "тест-кейсы, баг-репорты" }
```

Ответ: `{ "ok": true, "roles": { "<slot>": { "role": "...", "source": "assigned" } } }`.

Ограничения и ошибки:

- `slot` валидируется как `/^[a-z0-9-]+$/` (то же имя, что `- name:` члена в
  `cordis.patch.yml`); неизвестный слот — ошибка, а не создание нового;
- `role` — строка до 200 символов; пустая строка допустима (сброс в «не
  назначена»), но это тоже смена роли — только по просьбе пользователя;
- роль сохраняется на диск сразу (`roles.json`), переживает перезапуск DSH.

Примеры (порт — тот, на котором поднят веб-сервер DSH; ниже `$DSH`):

```bash
# curl
curl -X POST "$DSH/plugins/dsgs-agent-roster/role" \
  -H 'content-type: application/json' \
  -d '{"slot":"qa-tester","role":"тест-кейсы, баг-репорты"}'
```

```powershell
# PowerShell
Invoke-RestMethod -Method Post -Uri "$DSH/plugins/dsgs-agent-roster/role" `
  -ContentType 'application/json' `
  -Body '{"slot":"qa-tester","role":"тест-кейсы, баг-репорты"}'
```

Посмотреть текущие роли: `GET /plugins/dsgs-agent-roster/state` → поле
`roles: { slot: { role, source } }`. Память слота:
`GET /plugins/dsgs-agent-roster/memory/<slot>` (markdown).

Остальные 38 слотов (специалисты, инженеры движков, операции) получают роль при
первом назначении — либо капитан назначает её под задачу, либо субъагент
предлагает формулировку в отчёте. Пустая роль — нормальное стартовое состояние,
а не ошибка.

## Связка «роль → память → журнал»

1. Перед задачей субъагент читает `~/.dsh/agents/memory/<slot>.md`: раздел
   `## Роль` — что от него ждут, `## Сделано` — что он уже делал.
2. После задачи дописывает одну строку в `## Сделано`
   (`- YYYY-MM-DD · итог`) и при пустой роли предлагает её капитану.
3. События задач складываются в `~/.dsh/agents/activity.jsonl`; клиент студии
   показывает последние 10 дел в карточке субъагента — это производная от
   `team.json` и журнала, отдельно заполнять не нужно.

Подробности формата памяти и пример заполнения — `studio/memory-template.md`.
